# 2026-08-22 — Тестовий прогін content-semantics-agent на site24.com.ua

## Контекст

Катерина попросила прогнати skill `content-semantics-agent` на власному сайті Site24
як тестовий кейс — щоб побачити результат і скоригувати сам skill. Робота велась через
зовнішній пайплайн `D:\Claude\Clients\site24-seo-pipeline\` (поза цим репозиторієм) —
там і лежать усі артефакти нижче.

## Що зроблено

1. Заскафолжено нового клієнта `site24` у пайплайні (`clients/site24/`).
2. Дані Google Search Console витягнуто через Chrome (browser fallback — OAuth API для
   цього клієнта не налаштований): 3 місяці, властивість `sc-domain:site24.com.ua`.
   Топ-250 запитів із 1000 і всі 107 сторінок → `clients/site24/data/gsc-export/2026-08-22/`.
3. Чорновий `config.yml` (content_pillars, ICP, money_pages, site_type, languages)
   складено з доказів і **підтверджено Катериною** в чаті:
   - 5 пілорів: SEO-просування, PPC/контекстна реклама, AI-просування, Ціни/вартість,
     Кейси/портфоліо (окремий пілар, підтверджено)
   - ICP: власники бізнесу/маркетинг-директори, Київ/Україна → міжнародний; сигнал
     "може бути трафік конкурентів" — залишено як відкрите питання, не фільтрується
   - money_pages: тільки `/kontakty/` — окремих сторінок замовлення нема, конверсія
     через кнопки замовлення + чат на кожній сторінці
   - site_type: **catalog** (кластер = сторінка послуги, не блог hub-and-spoke)
   - languages: **тільки RU** цього разу (UA — окремий повний прогін пізніше)
4. Повний прогін Фаз 0–6 (seo-cluster skill) по всіх 5 пілорах, RU:
   `clusters/ru-catalog-2026-08-22/cluster-plan.md` + `structure.md`, і датований
   батч у `BACKLOG.md` (13 ідей).
5. За командою "роби далі" — дзеркальний повний прогін для UA (той самий набір
   seed-термінів, ті самі 5 пілорів): `clusters/ua-catalog-2026-08-22/`, ще 13 ідей
   у `BACKLOG.md`. `config.yml.languages` оновлено на `[ru, ua]`. Порівняння двох
   прогонів підсилило знахідку про RU/UA канібалізацію (RU: 296K показів на ціновій
   сторінці, UA: лише 12.8K на ту саму тему — розрив 23×, ще виразніший, ніж
   здавалось по одному RU-прогону).

## Ключові знахідки

- **Аномалія цін RU/UA:** `/ru/czini-na-prosuvannya-ta-rozkrutku-sajtiv/` дає ~48%
  усіх показів сайту (296K з 613K, 3 міс) на позиції ~48. UA-версія тієї ж теми —
  лише 12.8K показів. Канібалізація підозрюється, але не підтверджена — треба
  Query×Page join (OAuth), якого зараз нема. Катерина про це не знала.
- Архітектура сайту (RU) вже майже ідеально відповідає кластерам — 12 із 13
  кластерів мають живу сторінку, що вже ранжується. Реальний важіль росту —
  не новий контент, а чому наявні сторінки сидять на позиціях 30–60 (технічні/
  авторитетні фактори — поза межами цього skill'а). Єдиний реальний "створити нову
  сторінку" кандидат — Amazon Ads (зараз лише блог-пост, не сервісна сторінка).
- **Обмеження інструментарію:** `WebSearch` у цій сесії — US-only, ~5–7 посилань з
  AI-サマарі, не верифікований топ-10 для google.com.ua. Жодного результату із
  site24.com.ua чи українських конкурентів. Через це жоден Phase 2 висновок не
  дотягнув до тіру `Confirmed` — все `Hypothesis`. Це найбільше, що варто виправити
  в skill перед бойовим використанням.

## Оновлення (той самий день) — триаж RU/UA цінової пари

За командою "продовжуй робити по алгоритму" пішла на Крок 5 skill'а
(Cannibalization check). Автоматична детекція (`seo_baseline.py`) недоступна без
OAuth, але Крок 3 методу (Triage — verify live) не потребує OAuth — зробила його
вручну для флагованої пари цінових сторінок:

- `curl -I`/`curl -IL` на обидві сторінки → обидві живі (200), без редиректів
- Перевірка `<head>`: **hreflang коректний** (uk/ru/x-default), кожна сторінка
  сама-канонікалізується правильно, розмір сторінок порівнянний

**Висновок: це НЕ канібалізація і не hreflang-баг.** Це технічно правильна
білінгвальна пара — 301/merge тут був би помилкою. Розрив у показах (296K RU
проти 12.8K UA) реальний, але причина ще не встановлена (гіпотези: перевага
RU-мовного попиту в цій ніші vs. RU-сторінка збирає ширший/менш точний набір
запитів) — обидві потребують Query×Page join, якого немає.

**Виправила попереднє формулювання** ("підозра на канібалізацію") у `config.yml`,
обох `cluster-plan.md`, обох `structure.md` і обох батчах `BACKLOG.md` — старий
рядок закреслено з поясненням (за конвенцією файлу), не видалено. Новий звіт:
`clients/site24/reports/triage-ru-ua-pricing-2026-08-22.md`.

## Оновлення (той самий день) — спроба DataForSEO enrichment

Питала, чи запускати OAuth GSC setup для глибшої канібалізаційної діагностики —
Катерина відмовилась ("інше наступне без OAuth"), обрала DataForSEO enrichment
(Phase 3.5, опційний крок) для вже зібраних 13 RU + 13 UA seed-термінів (~26
ключових слів, далеко нижче межі 200, де потрібне окреме підтвердження).

**Знайдено і виправлено реальний баг у пайплайні:** `scripts/keyword_enrich.py` мав
жорстко закодовані `language_code: "en"` / `location_code: 2840` (США) — для
будь-якого не-англомовного клієнта це або поверне порожні "n/a", або дані не того
ринку, видані за реальні. Додала `--language`/`--location` (підтвердила через
DataForSEO docs: Ukraine = `2804`, мови `ru`/`uk`). Це вплине на всіх майбутніх
клієнтів пайплайна, не тільки site24 — варто занести в TODO пайплайна окремо.

**Сам виклик заблокований на рівні акаунту DataForSEO**, не коду: API повертає
`403 — Please verify your account` (`app.dataforseo.com`). Креденшели в `.env` на
місці, це не проблема авторизації запиту — акаунт не пройшов верифікацію на боці
DataForSEO. Я не можу це виправити (потрібен логін власника акаунту в їхній
кабінет). Файли `keywords.txt` (RU/UA) готові в `clusters/{ru,ua}-catalog-2026-08-22/`,
команди для запуску після верифікації — записані в чаті.

**Рішення Катерини:** зафіксувати це як черговий пункт для калібрування skill'а і
зупинитись тут ("те, що зараз").
